# Data Sprint 2 — Local Kenya

Implemented 26 August 2026.

Data Sprint 2 turns the existing Kenya → County → Constituency → Ward geography skeleton into the Atlas's first **fully populated local drill-down**. The indicator is the IEBC certified 2022 registered-voter schedule because it is one of the few national datasets published on exactly the electoral geography used by the Atlas.

## Acceptance scope

Sprint 2 is complete only when all of the following are true:

- **47/47 counties** remain reconciled to the audited Sprint 1 county schedule;
- **290/290 constituencies** have a registered-voter observation;
- **1,450/1,450 County Assembly Wards** have a registered-voter observation;
- every ward joins by its IEBC numeric ward code to the canonical geography registry;
- every ward's canonical parent is the source constituency and every constituency's parent is the source county;
- the 1,450 ward values sum exactly to **22,102,532**;
- each of the 47 county sums reconstructed from wards equals the Gazette Third Schedule county value already used in Sprint 1;
- constituency totals are exact sums of their child ward observations and are clearly marked **B — Official derived**;
- ward observations are marked **A — Official direct** and cite the IEBC Gazette First Schedule;
- no county value is copied or allocated to a constituency or ward;
- the map can visibly drill Kenya → county map → constituency map → ward map using real values at every level;
- automated CI fails if any of these guarantees is lost.

## Primary source

**Independent Electoral and Boundaries Commission / Kenya Gazette, 21 June 2022, Gazette Notice No. 7290.**

Official publication:

<https://www.iebc.or.ke/uploads/resources/L7k6ob1bau.pdf>

The notice contains:

1. **First Schedule** — Registered Voters per County Assembly Ward;
2. **Second Schedule** — Registered Voters per Constituency;
3. **Third Schedule** — Registered Voters per County.

The Atlas treats the Gazette as the statistical authority.

## Statistical treatment

### Ward

Ward values are **A — Official direct**.

Each observation corresponds to one row in the IEBC First Schedule. The Atlas records the Gazette page for each ward code and joins the value to the canonical ward using the numeric CAW code.

### Constituency

Constituency values are **B — Official derived**.

The Atlas sums the directly published IEBC ward values belonging to each canonical constituency. This is preferable to pretending an aggregate generated by the Atlas is a separately transcribed direct observation. Selected derived totals are locked against published Second Schedule anchors.

### County

Sprint 1 already contains the direct official Third Schedule county values. Sprint 2 independently reconstructs all 47 county totals from the 1,450 ward rows and requires exact equality with those existing county observations before publication.

## What the user can now do

Select **Registered voters** in the map and drill:

```text
Kenya
  → Nyandarua County
      → Ol Kalou Constituency
          → Kaimbaga Ward
```

At Kenya level the 47 counties are shaded with county observations. At county level the constituencies are shaded with official-derived totals. At constituency level all child wards are shaded with direct official IEBC values. Clicking a ward retains the ward sibling comparison and displays the exact ward observation.

The coverage chip changes with geographic level so the interface does not imply coverage that is not actually present.

## Runtime architecture

`assets/sprint2-data.js` wraps the Sprint 1 registry overlay. It validates the pinned coded source before adding **1,740 local series and 1,740 local observations**:

- 290 constituency series/observations;
- 1,450 ward series/observations.

It adds one documented local IEBC dataset/release and extends the existing `IND-REGISTERED-VOTERS` indicator to ward level. No new county observation is generated by Sprint 2.

`assets/sprint2-ui.js` adds level-aware coverage and provenance wording.

## Automated validation

Run:

```bash
npm test
```

or specifically:

```bash
npm run sprint2:validate
```

The Sprint 2 validator checks source pinning, full 47/290/1,450 code coverage, canonical hierarchy, national and county reconciliation, independent transcription agreement, Gazette anchors, script load order, provenance classes and anti-inheritance guards.

## Known architectural migration

Sprint 1 and Sprint 2 currently publish through additive static registry overlays so the GitHub Pages application can expose the data immediately without shipping multi-megabyte regenerated registries on every change. This is a **publication-architecture migration item**, not a missing Local Kenya observation.

A future data-engineering sprint should move both overlays into the native seed/build pipeline and archive the source extracts/checksums locally so the same series are emitted directly in `data/indicators/registry/*`. Until then, CI treats the overlays as first-class release code and validates their complete data contract before publication.
